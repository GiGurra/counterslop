# Working on counterslop

Browser parody shooter: one Go binary (`main.go`, `internal/game`) serves the embedded
client in `web/` (Preact + htm via import map, no JS build step) and the `/ws` game socket.
(`AGENTS.md` is a symlink to this file: one set of instructions for every agent.)

## Architecture at a glance

```
 browser (web/, plain ES modules)                 server (one Go binary)
 ┌─────────────────────────────────────┐          ┌──────────────────────────────────┐
 │ ui/ (Preact HUD, menus, console)     │          │ internal/app   HTTP: page, /ws,  │
 │ game/main.js  glue, input -> cmds    │  /ws     │                /maps.json, /dev  │
 │  ├ localsim.js  predict own cmd ─────┼─ cmds ──>│ internal/game  100 Hz ticks:     │
 │  ├ predict.js   reconcile, replay    │<─ snap ──┤   runCmd (move, weapons, hits),  │
 │  ├ arsenal.js   weapons (presenter)  │          │   rounds, economy, bots, nades   │
 │  └ *.gen.js  ◄── generated from Go ──┼── cmd/gojs ── internal/sim, game/*_shared.go│
 │ engine/ (WebGL renderer, audio, net) │          │ internal/content  maps, prefabs  │
 │ gen/ + assets/ (procedural assets)   │          └──────────────────────────────────┘
 └─────────────────────────────────────┘
```

- **The server is the authority** for every piece of gameplay state. The client predicts
  its own player by running the **same code** (generated from the Go, see below) on its own
  commands and reconciles with every snapshot.
- **The simulation and the model are written once, in Go**: movement (`internal/sim`), the
  command input, weapon rules, recoil, spread, shot angles, the player model's pose and hit
  test, the seeded PRNG and deterministic math. The client runs JS translated from it.
- **Everything visual and audible is the client's own** (hand-written JS): renderer,
  shaders, materials, sounds, voice, HUD, menus, effects. All procedurally generated.
- **Maps are Go** (`internal/content/maps`, built from prefabs + mapgen), sent to the client
  as data (`/maps.json`); the client draws them, the server collides with them.

## Finding your way

- Start at the entry points: `main.go` (CLI, `Params`) -> `internal/app` (HTTP) ->
  `internal/game/server.go` (connections, ticks) -> `simtick.go` (`runCmd`: one command:
  move, switch, reload, fire, hits). On the client: `web/index.html` -> `web/game/main.js`.
- Gameplay rules: `internal/game/*_shared.go` and `internal/sim` (generated to the client),
  the rest of `internal/game` (rounds, economy, buy, bots `ai*.go`, grenades, GPU Drop) is
  server only and reaches the client as snapshot state.
- Design notes: `docs/` (`shared-logic.md`: the Go -> JS generator and why; `gpu-drop.md`:
  the GPU Drop mode). Testing: `TESTING.md`. Player-facing: `README.md`.
- Data the client and server share as files: `web/assets/weapons/weapons.json`,
  `web/assets/economy.json`, `web/assets/models/player.json` (both sides load them).
- `rg '//gojs:shared'` lists the Go files that become client code; `rg -l 'gojs:extern'`
  the hand-written halves.

## Standing rule: sim and model code is written in Go, never hand-written in JS

The client's simulation and model code is **generated** from Go by `cmd/gojs` (a
translator for a deterministic subset of Go; `docs/shared-logic.md`). Generated files end
in `.gen.js` and start with `// Code generated by cmd/gojs ... DO NOT EDIT.`

| Go source (the one copy)                          | generated JS              | JS adapter (API, presentation) |
|---------------------------------------------------|---------------------------|--------------------------------|
| `internal/sim` (movement, collision)              | `web/engine/sim.gen.js`   | `web/engine/physics.js`        |
| `internal/detmath` (sin/cos/exp/hypot, same bits) | `web/gen/detmath.gen.js`  |                                |
| `internal/content/rng` (mulberry32)               | `web/gen/rng.gen.js`      | `web/gen/rng.js`               |
| `internal/game/*_shared.go`: command input, weapon rules, recoil, spread, shot angles, move speed, player model pose + ray test | `web/game/shared.gen.js` | `web/engine/cmd.js`, `web/game/arsenal.js`, `web/gen/boxmodel.js`, `web/game/tags.js` |

- **Never write or edit simulation/model logic in JS.** Change the Go, then
  `go generate ./internal/gojs` and commit the `.gen.js` with it. CI fails a commit whose
  generated JS is stale (step "generated JS up to date": `go run ./cmd/gojs -all -check`).
- New shared logic: put it in a `//gojs:shared` file (the directive above `package`) of
  `internal/game`, or a package listed in `internal/gojs/targets.go` `Targets`. Call the
  generated function from a thin JS adapter; keep the adapters' public APIs stable so
  callers and tests don't change.
- The subset (gojs package doc): no goroutines, defer, interfaces, embedding, generics,
  named results. Value params and range values are read-only (copy to a local first).
  The translator says what is wrong and where.
- **Determinism**: products next to a `+`/`-` need a `float64(...)` rounding barrier (Go
  fuses `a*b+c` into an FMA on arm64; JS never does); the translator rejects unwrapped
  ones and `TestNoFusedMultiplyAdd` checks the arm64 assembly. Use `detmath` instead of
  `math.Sin/Cos/Exp/Hypot`; sum map entries in sorted key order (Go map order is random).
- Opting out, for a hand-optimised or browser-only piece: `//gojs:skip` on a declaration
  (not translated; shared code may not call it), `//gojs:extern ./file.js` on a function
  (imported from a hand-written module, e.g. `web/game/hitbox.extern.js`). Each needs a
  reason in a comment and a test pinning the JS to the Go.
- Still hand-written on the client, on purpose: `localsim.js` (orchestrates one predicted
  command over the generated pieces), `predict.js` (reconciliation), and everything
  presentational.

## Standing rule: every asset is generated by us

Every texture, model, sound and other asset is our own and generated procedurally or
algorithmically, either at runtime (GLSL shaders, WebAudio synthesis, code-built geometry)
or at build time by a generator script checked into this repo.

- No downloaded or third-party art, audio, fonts-as-assets, or models.
- No binary assets (png/jpg/wav/ogg/mp3/glb/…) committed by hand. If a generator emits
  one, commit the generator; prefer generating at runtime.
- No `texImage2D` from image files; procedural textures rendered by our own code are fine.
- Vendored *code* (e.g. `web/vendor/preact`) is allowed, with its license next to it.

## Standing rule: the server owns all gameplay state; the network may lose anything

- Every piece of gameplay state (body, HP/dead, team, weapons: inventory, current slot,
  ammo, reload/bolt/fire timers; later money, round state) is decided by the server and
  carried in **every** self-snapshot (`me` in `snap`). The client predicts it by running
  the same rules (the code generated from internal/sim and internal/game/*_shared.go) on its own
  commands, compares at the acked command and, on any difference, adopts the server's
  state and replays the unacknowledged commands (web/game/predict.js, reconcileWeapons
  in main.js). Correctness never depends on an event message arriving.
- Design every message as if the transport were unreliable datagrams (lost, duplicated,
  reordered), even on websockets: each command packet repeats the last unacked commands
  (the server dedupes by seq); snapshots carry the server tick, are full self-state, and
  an older one than the newest seen is dropped. Events (kill feed, sounds, effects) are
  optional. Anything that must arrive goes through state, or a small reliable channel
  (seq + ack + resend) on top.
- Changing gameplay rules means changing the Go (the client's copy is generated) and the
  shared tests (golden vectors, sim/cases). Sim `resync-faults` (net_fakeloss/dup/reorder + exactly lost
  commands) must converge.

## Shipping

- Small working commits straight to `main`; a push to `main` deploys to
  counterslop-test.gigurra.se within about a minute (check `/version`; on this host `curl 127.0.0.1:8481/version` skips Cloudflare Access).
- prod follows the `prod` git tag. Move it only when the operator says so.
- CI (`.github/workflows/ci.yml`, workflow `ci`: jobs `test` + `sim`, and a final job `ci` that
  needs both) gates deploys: test and prod only deploy commits whose `ci` check run is green.
  If main goes red, fixing it comes first.
- Releases: a `v*` tag (e.g. `v0.2.0`, on a green main commit) runs `.github/workflows/release.yml`:
  the full `ci` (via `workflow_call`), binaries for linux/darwin amd64/arm64, a GitHub release and the
  Homebrew formula in GiGurra/homebrew-tap. `v*` tags never deploy. Keep the job name `ci` and the
  `workflow_call` trigger in ci.yml.
- Tag `prod` only on a commit whose `ci` check is green (normally main's head once CI finishes).
  A commit whose run was cancelled (superseded by a newer push) won't deploy; if it really must
  go out, re-run its CI in GitHub, then the operator runs `sudo counterslop-deploy prod --force`.
- Build: `go build -ldflags "-X main.version=$(git rev-parse --short HEAD)" -o counterslop .`
- Dev: `go run . --addr 127.0.0.1:8080 --dev web` serves `web/` from disk for live edits.
  The CLI is a boa struct (`Params` in main.go): long flags take two dashes, there are no
  one-letter flags, and `--help` lists each flag's env var (`COUNTERSLOP_ADDR`, ...).
- Check `go vet ./...` and load the page in a browser before pushing.

## Where things go

Keep **algorithms** (reusable, pure, seeded, no game state) apart from **definitions**
(what this game looks and sounds like), so new maps and features reuse instead of rewrite.

```
web/
  engine/     game-agnostic runtime: gl.js renderer (takes palette/materials/sky, draws
              map + generic solids), math, loop (frame pacing), input, net, physics.js
              (adapter over sim.gen.js), cmd.js (command bits, over shared.gen.js)
  ui/         hud (Preact), console, settings (one store: options menu = console cvars)
  game/       main.js glue: gameplay, networking, wiring assets into the engine;
              shared.gen.js (generated game rules), arsenal.js (weapons: generated
              rules + sounds/HUD/viewmodel), localsim.js + predict.js (prediction)
  gen/        ALGORITHMS
    glsl/     noise (hash, noise, fbm), patterns (tiles, bricks, edgeDist, stripes,
              gridLine), lighting (light, fog), shadow (sun shadow-map PCF);
              index.js assembles chunks + palette consts
    synth/    WebAudio primitives: env, osc, noise, filter, vibrato, dest (pan/gain);
              fx.js: seeded reverb impulse response, sample playback with reverb send
    voice/    SlopVox formant speech synth (pure, seeded, runs in Node): ARPAbet phoneme
              table, Klatt-style renderer, sample FX (stutter, drive, bitcrush, mix)
    rng.js    seeded mulberry32 (adapter over rng.gen.js, from internal/content/rng)
    boxmodel.js  box-built model pose for drawing; parts + ray test from shared.gen.js
    detmath.gen.js  deterministic math (from internal/detmath)
    color.js  colour helpers
  assets/     DEFINITIONS built on gen/
    palette.js        the one shared palette; GLSL sees it as PAL_<NAME> constants
    materials/        one file per material: GLSL `vec3 mat_<name>(Surf s)`; list it in index.js
    sounds/           recipes on gen/synth; add to CATALOG in index.js
    voice/            announcer voices + lines as phoneme strings (lines.js), playback queue
    models/           box-built models returning render parts (player, toy gun)
    sky.js            sky shader + sun direction
  dev/assets.html     gallery at /dev/assets: every material, model and sound
internal/
  app/                HTTP wiring: the page, /ws, /maps.json, dev routes
  game/               websocket game server; *_shared.go are also the client's rules
  sim/                movement and collision (the client runs it as sim.gen.js)
  detmath/            deterministic sin/cos/exp/hypot for shared code
  gojs/               the Go -> JS translator (cmd/gojs; Targets in targets.go)
  content/            Box/Map types + material names (must match web/assets/materials)
    prefabs/          reusable props (Crate, CratePyramid, Wall, Pillar, Building, Stairs...)
    mapgen/           layout helpers (Builder, Enclosure, ...)
    maps/             map definitions from prefabs + mapgen; a golden file pins each map
    rng/              seeded PRNG; the client runs it as web/gen/rng.gen.js
cmd/
  gojs/               regenerate the client code: go generate ./internal/gojs (-check in CI)
  sim/                headless-Chrome scenarios and lockstep sim/cases
  simdiff/            what a change did to every sim/case trace
  balance/            time-to-kill tables
sim/                  cases/ (lockstep cases), scenarios/ (snapshots), registry-exempt.json
docs/                 design notes (shared-logic.md, gpu-drop.md)
```

- New material: `web/assets/materials/<name>.js` + register in `index.js` + add the name in
  `internal/content/content.go`. Use palette colours and gen/glsl patterns; add a new pattern
  to gen/glsl/patterns.js if it is reusable.
- New weapon or a stat change: data in `web/assets/weapons/weapons.json` (CS2 archetype values:
  damage, `armorPen`, `falloff` per 12.7 m, RPM via `interval`, mag/reserve, reload, price, and the
  `recoil` spray pattern: keyframes [shot, up, right] + `recover`, internal/game/recoil_shared.go), plus
  its target bands in `internal/game/testdata/balance_bands.json` (`TestBalanceBands` fails
  without them). `make balance` prints the time-to-kill tables (also in the CI summary).
- New sound: a recipe in `web/assets/sounds/`, exported and listed in `CATALOG`.
- New announcer line: add it to `LINES` in `web/assets/voice/lines.js` (hand-written ARPAbet,
  tune it in the gallery's SlopVox panel); it shows up in the gallery and `say_announcer`.
  Kill triggers live in `web/game/announcer.js` (`onKill({headshot})`, `onDeath`, `onRoundStart`).
- New prop: a prefab in `internal/content/prefabs` (and a model in `web/assets/models` if it
  is not map geometry).
- New map: `internal/content/maps/<name>.go` built with mapgen + prefabs, registered in `All`
  and `Order` (the rotation and selector order). It needs sites A and B, team spawns inside buy
  zones (`BuyAroundSpawns`), a nav graph from each team's node (`vibe`, `artisan`) to both sites
  (`TestWalkToSites` walks it with the real movement code), `Meta` text, a golden file
  (`UPDATE=1 go test ./internal/content/maps`) and a `sim/scenarios/map-<name>.json`. Previews
  for the Maps screen and the vote are rendered on the client from `/maps.json`; there are no images.
- Anything random takes a seed (gen/rng.js / content/rng) so every client sees the same thing.
- Check new assets in the gallery (`/dev/assets`) before shipping.
- Changing de_slop on purpose: `UPDATE=1 go test ./internal/content/maps` rewrites the golden file.

## Tests (see TESTING.md)

- `make test-fast` (seconds) before every push; `make test` for what CI runs.
- **Every bug fix lands with a test that failed before the fix.** Every feature lands with unit
  tests, plus a scenario assertion or sim/case if it is user-visible. A new command, bind or cvar
  needs a sim/case that exercises it (the CI action-registry check enforces this).

## What a change does to gameplay: sim/cases and simdiff

After any gameplay change (movement, weapons, items, damage, commands), first run

    go run ./cmd/simdiff            # vs HEAD~1; `go run ./cmd/simdiff main` vs main

It runs every `sim/cases/*.json` case on the base and on your tree, on the server
(go) and in the client predictor (js), and lists per case which state fields
changed, from which tick, by how much. Confirm it shows exactly the intended
effect ("the Prompt's fire rate changed in auto-fire-rate and reload; nothing else
moved") before pushing. CI posts the same report against the previous commit.

- A case is players + a per-tick command script + expectations (format at the top
  of `web/game/cases.js`). `go test ./...` runs every case through the server
  (`internal/game/cases_test.go`), the client predictor (`web/game/cases.test.mjs`)
  and `TestCasesAgree`, which fails on the first tick where server and client
  disagree on any shared field.
- `go run ./cmd/sim -cases [name...]` runs the cases end to end in **lockstep**: the real
  server (its ticker paused, stepped one tick at a time) and a headless client per player,
  each command going in through the client's real key/mouse/wheel events on its binds.
  Every tick the client's prediction and the server must agree; expectations are checked
  on both. `act` (lastinv, invnext, ...), `hold` (+showscores) and `exec` (a console line)
  inputs reach UI actions and console/admin commands. ~25 s for all cases (`-j 4`).
- **Action registry:** a full `-cases` run reads every bindable action, command button,
  console command, client cvar and admin/rcon command from the live client and server, and fails if
  one has no passing case exercising it (coverage comes from the cases' inputs). A new
  action, command or cvar needs a case (or an entry with a reason in `sim/registry-exempt.json`);
  a case covers a cvar by setting it with `exec` (and restores it at the end).
  The matrix is in the CI job summary.
- Weapon rules also have shared golden vectors (`internal/game/testdata/weapons_golden.json`,
  `UPDATE=1 go test ./internal/game -run TestWeaponGolden` regenerates them on purpose).

## Seeing the game without a display

`go run ./cmd/sim [scenario...]` (or `make snapshots`) starts the real server in-process in test
mode, drives headless Chrome clients through scripted scenarios and writes
`out/snapshots/<scenario>/<NN>-<shot>-<client>.png` plus a `.json` state dump (client state,
server `/debug/state`, page errors) for each snapshot, and a contact sheet at
`out/snapshots/index.html`. Open the PNGs with your image viewer / Read tool.

- Scenarios are JSON in `sim/scenarios/` (format documented at the top of `cmd/sim/main.go`):
  join (players start spectating; `join` picks `auto` unless given a team, `team` switches),
  teleport/turn/crouch (`set`), hold keys / fire (`hold`), step N frames at a fixed 1/60 s,
  wait for the network (both in lockstep: the server only ticks when the run steps it, so a
  scenario plays the same under load; `"realtime": true` only for wall-time subjects like
  pacing, audio or fake lag; a failed step dumps `fail-<client>.*`), force UI states (`ui`: play, menu, options, controls, maps, console, scoreboard, teammenu),
  run console commands (`exec`), free camera (`camera`: overview, orbit, explicit), pin the
  shader clock (`time`), hide the HUD (`hud`), then `snapshot`.
- The test API is `window.__cs` (`web/game/testapi.js`). It only exists when the server runs
  with `--test` AND the page URL has `?test=1`; prod never passes `--test`. Test mode also turns
  off the server's speed checks so scenarios can teleport.
- `-dev web` (the default) serves the client from disk, so client edits show up without
  rebuilding. Chrome is found on PATH or via `$CHROME`.
- Golden images (advisory): `go run ./cmd/sim -update-golden` stores the current shots in
  `sim/golden/`; `-diff` compares against them with a pixel tolerance.
- Add a scenario whenever you build something visual, and look at the snapshots before pushing.
- Native browser dialogs (e.g. the beforeunload "Leave site?") can't be captured headless; ask
  the operator to check those by hand.
